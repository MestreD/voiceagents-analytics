# VoiceAgents analytics

A dbt project that models the usage and billing of an AI voice agent sold to
Spanish *gestorías* (tax and accounting firms). The agent answers inbound calls,
handles what it can, and hands the rest to a person.

The warehouse is DuckDB and the data is synthetic, generated by a script in this
repo. Clone it, run two commands, and you have the whole thing building locally
in under a minute.

[![dbt build](https://github.com/USERNAME/voiceagents-analytics/actions/workflows/ci.yml/badge.svg)](https://github.com/USERNAME/voiceagents-analytics/actions/workflows/ci.yml)

---

## Why synthetic data

The modelling patterns here are the ones I use in production, but the data is
not. `scripts/generate_data.py` builds the three raw tables from a fixed seed,
so every clone of this repo produces byte-identical data and the tests in CI
mean something. Nothing in this repo comes from an employer.

The generator is not a toy. It encodes the things that make the modelling
non-trivial: a customer base that grows over 18 months, churn, the Spanish
filing calendar (quarterly VAT spikes in January, April, July and October, the
June income-tax deadline, a dead August), call intents with different resolution
rates, and a price list that changes three times during the period.

## Quickstart

```bash
pip install -r requirements.txt
python scripts/generate_data.py
export DBT_PROFILES_DIR=.          # Windows: set DBT_PROFILES_DIR=.
dbt build
```

That generates the raw CSVs, builds every model, and runs every test.

## Sources

Three raw tables, read straight off disk by DuckDB rather than loaded as dbt
seeds, because that is closer to how a real project reads an external stage.

| Table | Grain | Notes |
|---|---|---|
| `raw.gestorias` | one row per customer firm | current state only, no history |
| `raw.pricing` | one row per plan per validity window | `valid_from` inclusive, `valid_to` exclusive, open row has null `valid_to` |
| `raw.calls` | one row per call | ~110k rows over 18 months |

## Model layers

```
staging/        one model per source: rename, cast, booleans. No joins.
intermediate/   the joins and the reusable logic. Not exposed to BI.
marts/          what a consumer queries. Documented grain, tested keys.
```

### Planned marts

| Model | Grain | What it is for |
|---|---|---|
| `fct_calls` | one row per call | incremental; the base fact for volume, resolution and handling-time analysis |
| `dim_gestorias` | one row per firm per version | SCD Type 2 via dbt snapshot, so plan changes are tracked rather than overwritten |
| `fct_gestoria_monthly_billing` | one row per firm per month | the interesting one: see below |

### The billing model is the point of this repo

`fct_gestoria_monthly_billing` totals each firm's minutes for a month, then
joins the pricing row that was **in force on that month's last day**, and splits
the result into included minutes and overage to produce the invoice amount.

That is an as-of join against a slowly-changing source, and getting it wrong is
the single easiest way to misstate revenue. Three specific traps:

1. Joining on `plan_code` alone fans the result out across every historical
   price. The join needs the validity window.
2. Using the price in force *today* silently restates past months the moment a
   price changes.
3. `valid_to` being exclusive matters: a price starting on the 1st and one
   ending on the 1st must not both match.

The tests on this model assert the grain is unique, that no month fans out, and
that every billed month resolved exactly one price.

## Known limitations

`raw.gestorias` carries current state only, so the `dim_gestorias` snapshot can
only capture changes from the moment snapshotting starts. A real source would
either ship change data capture or an audit table. This is called out rather
than hidden because it is the kind of thing worth asking about in a design
review.
